## Approved user journey

One already-extracted documentation claim (a MasterSlide topic, or any other pre-parsed source — this slice does not parse raw documents itself), plus zero or more Evidence ids and a caller-supplied dual-key contract (`product_key`, `documentation_key`), is compared against whatever approved/current Editorial Memory already exists for those exact keys. The result is a read-only report: what was retrieved, whether the cited Evidence is actually relevant (backed by an independently persisted relationship, not merely resolvable), and — using only bounded, deterministic structural rules this slice is authorized to apply — either a relation candidate (`NEW`/`CONFIRMS`, the only two reachable in this slice) or an explicit unresolved state with a stated reason. Nothing is written to Editorial Memory; a human (or a later, separately-authorized slice) decides what, if anything, to propose from the report.

## Functional requirements (current, post-Repair-Round-2)

- `documentation_intelligence.compare.compare(memory, *, claim_text, source_ref, feature_area, product_key=None, documentation_key=None, evidence_ids=(), include_proposed_documentation=False) -> ComparisonReport` — the slice's one entry point. (Repair Round 2: `expected_verification_scope` removed entirely — see DI-S1-01 below.)
- **Retrieval**: exact-key only, via unmodified `retrieval.get_current_by_key`. `product_key` and `documentation_key` are independent, caller-supplied identifiers — no automatic subject mapping, no fuzzy/embedding/vector matching anywhere in this slice.
- **Knowledge-type enforcement, unconditional**: the exact KnowledgeItem `product_key` resolves to (if any exists at all, regardless of lifecycle status — proposed-only, current, or otherwise) must be `KnowledgeType.PRODUCT`; the exact item `documentation_key` resolves to must be `KnowledgeType.DOCUMENTATION`. A wrong-type key raises the existing, reused `KnowledgeTypeMismatchError` rather than being silently accepted under the opposite role — checked before any lifecycle-status branching, per Repair Round 2 (DI-S1-02).
- **Documentation retrieval symmetry**: the documentation side tries `get_current_by_key` first, exactly like the product side (a documentation KnowledgeState can be approved and `current`, same as any other). A `proposed`-only documentation state is surfaced only when the caller explicitly opts in via `include_proposed_documentation`, and is always labeled `"proposed"` in the report — but the type check above applies regardless of this opt-in.
- **Evidence relevance — independently persisted relationship only** (Repair Round 2, DI-S1-01): a cited Evidence id must resolve (`get_evidence`, raises typed `UnknownEvidenceError` otherwise) *and* already appear in `evidence_refs` of *some* state (any lifecycle status) already recorded on the KnowledgeItem `product_key` resolves to. No caller-supplied scope, tag, or metadata of any kind can establish relevance — the prior `expected_verification_scope` mechanism was removed because scope-overlap between two caller-influenceable inputs (the Evidence's own declared scope and the caller's "expected" scope) could be trivially fabricated to make unrelated Evidence appear relevant. If `product_key` resolves to no KnowledgeItem at all, there is no persisted structure of any kind to check against, and the comparison fails conservatively: `evidence_sufficiency = "insufficient"`, `relation_candidate = None`.
- **Relation reasoning is Slice 1's own, bounded, and deterministic** — never a caller-supplied assertion. Only two non-null outcomes are reachable in this slice, both requiring relevant Evidence (per the rule above): no current product Knowledge + relevant Evidence → `NEW`; current product Knowledge + incoming claim text exactly equal (whitespace-normalized only, no case-folding, no similarity scoring) to the current content + relevant Evidence → `CONFIRMS`. Every other case — including any case that would eventually become `REFINES`/`CONTRADICTS`/`SUPERSEDES` — is `unresolved`, with a stated reason. This is a founder-accepted, deliberate scope boundary: distinguishing those three relations from arbitrary differing text requires semantic judgment (LLM/embeddings/fuzzy matching), which this slice is explicitly barred from using.
- **`product_change_signal`** is derived from `relation_candidate` via a fixed lookup table (`CONFIRMS`/`REFINES` → `"none"`; `CONTRADICTS`/`SUPERSEDES` → `"possible"`; `NEW` → `"not_applicable"`; no candidate → `"unresolved"`) — it never gates or influences what `relation_candidate` is allowed to be.
- **`documentation_vs_product`** is capped at `{"aligned", "differs", "not_comparable"}` (exact normalized-text comparison only) — `"conflicts"` is not a reachable value, since distinguishing a genuine conflict from a benign restatement requires the same excluded semantic capability. This field never drives `relation_candidate` or `product_change_signal` in either direction (DOCUMENTATION CONFLICT ≠ PRODUCT TRUTH CHANGE).
- **Zero writes**: `compare()` calls only `get_current_by_key`, `list_current_by_feature_area`, and `get_evidence` — never a mutating `EditorialMemory` method. No `propose_state`, `approve_state`, or `ingest_existing_documentation` call exists anywhere in this module.
- **Import identity**: `_editorial_memory_import.py` guarantees at most one loaded copy of `editorial-memory/lib` process-wide, canonicalizing under the name `lib` regardless of whether this module or some other consumer (under any alias) loads it first (Repair Round 2, DI-S1-04). If `lib` is already bound to something genuinely unrelated and no already-loaded editorial-memory copy exists anywhere to canonicalize instead, the module raises `EditorialMemoryImportConflictError` before loading anything — it never falls back to loading a fresh copy under a private alias (Repair Round 3, DI-S1-04 residual). This package's own directory is named `documentation_intelligence`, not `lib`, so it never contends for that name.

## Audit 1 findings (Repair Round 1)

An independent Codex audit of Slice 1 Build 1 returned **FAIL**, finding 4 code-level defects plus 3 governance defects, all fixed in Repair Round 1:

1. **Caller-supplied relation as authoritative** — Build 1 accepted an `asserted_relation`/`asserted_documentation_vs_product` parameter and treated it as the source of truth, subject only to structural consistency checks. Fixed: both parameters removed entirely; relation/documentation-vs-product derived internally.
2. **Evidence sufficiency = mere existence** — Build 1 treated any resolvable Evidence id as sufficient. Fixed (Repair Round 1 version, later found still exploitable and fixed again in Repair Round 2 — see DI-S1-01 below): a two-test relevance check (already-linked-evidence, or caller-scope-overlap).
3. **No Knowledge-type enforcement** — Build 1's key resolution did not check `knowledge_type` at all. Fixed (Repair Round 1 version, later found incomplete and fixed again in Repair Round 2 — see DI-S1-02 below): `KnowledgeTypeMismatchError` on a mismatch, but only when a *current* state existed.
4. **Import collision, order-dependent duplicate identities** — Build 1's bridge loaded `editorial-memory/lib` under a fixed private alias from inside a sibling package that was itself also named `lib`. Fixed (Repair Round 1 version, later found incomplete and fixed again in Repair Round 2 — see DI-S1-04 below): package renamed `lib` → `documentation_intelligence`; bridge claims the canonical name `lib` for `editorial-memory/lib` when free.
5. **(Governance) Insufficient test coverage** — fixed: adversarial tests for unrelated Evidence, mismatched verification scope, swapped Knowledge types, both import orders, byte-level real-store immutability, relation reasoning itself.
6. **(Governance) No OpenSpec/governance record set** — fixed: this record set created.
7. **(Governance) Stale repository status documentation** — fixed: `docs/CURRENT.md`/`docs/DECISIONS.md` reconciled, recorded as `PROJ-030`.

## Re-audit 1 findings (Repair Round 2 — this record)

Independent Codex Re-audit 1 of Repair Round 1's diff returned **FAIL**, finding 3 further code-level defects and 3 further governance/test defects, all fixed in this same repair round:

1. **DI-S1-01 (Evidence relevance exploit)**: Repair Round 1's second relevance test — caller-supplied `expected_verification_scope` intersected against the Evidence's own `verification_scope` — let a caller fabricate apparent relevance for genuinely unrelated Evidence by supplying scope tags that happened to overlap, producing a positive `NEW`/`CONFIRMS` result with no real backing. **Fixed**: that mechanism removed entirely (the parameter no longer exists). Relevance is now exactly one test: the Evidence id already appears in `evidence_refs` of *any* state (any lifecycle status, not only current) already recorded on the resolved `product_key` KnowledgeItem — a relationship established through Editorial Memory's own normal propose/approve lifecycle at some point in the past, never through anything a single `compare()` call's own arguments assert about themselves. If no KnowledgeItem exists at all for `product_key`, the comparison fails conservatively (`insufficient`/`unresolved`) rather than inventing a substitute signal.
2. **DI-S1-02 (KnowledgeType enforcement gap for non-current items)**: Repair Round 1's type check only ran on the result of `get_current_by_key`, so an item with no current state (only proposed, or only invalidated/superseded) skipped the check entirely and silently resolved as if nothing existed. **Fixed**: `_resolve_typed_item` resolves and type-checks the exact referenced KnowledgeItem unconditionally, regardless of lifecycle status, before any current-state lookup happens — applied identically to `product_key` and `documentation_key`, including when `include_proposed_documentation=False`.
3. **DI-S1-04 (alias-first import identity gap)**: Repair Round 1's bridge correctly *reused* an already-loaded copy of `editorial-memory/lib` found under some other alias, but never *also* canonicalized it under the name `lib` — so a later, unrelated plain `import lib` elsewhere in the same process would find the name still unclaimed and freshly re-import the module from disk, creating a second, non-`is`-identical copy. **Fixed**: `_canonicalize_under_lib` registers an alias-discovered module under `lib` too (and re-registers any of its already-imported submodules under the equivalent `lib.<name>` keys), so every later import — under any name, in any order — converges on the single existing object. If `lib` is already bound to something genuinely unrelated, the module raises `EditorialMemoryImportConflictError` explicitly rather than proceeding under a private alias that could diverge.
4. **TEST-DI-01 (missing byte snapshot)**: one real-data test (`test_m_evidence_cited_but_not_linked_...`) lacked the before/after whole-store byte-hash bookend every other real-data test already had. **Fixed**: added; every test in `TestRealRegressionCases` now has it, with no exceptions.
5. **GOV-DI-01 (OpenSpec completeness)**: this file lacked the `docs/TESTING.md`-required Classification section (base tier, rationale, specialized profiles, independent-audit requirement). **Fixed**: see "Classification" above.
6. **GOV-DI-03 (stale `docs/INDEX.md`)**: `docs/INDEX.md` described `documentation-artifacts/bridge-ui-evidence/` as "empty until Browser Verification work resumes" — untrue, and had been untrue since well before this slice began (38 Evidence records, 2 KnowledgeItems). **Fixed**: `docs/INDEX.md` corrected to describe the real, populated store, and to explicitly delimit this slice's own integration scope (reads already-persisted Editorial Memory records only) from the unrelated raw `masterslide/` decks, `Expert resources/` videos, and build caches it does not touch or depend on.

## Re-audit 2 findings (Repair Round 3 — this record)

Independent Codex Re-audit 2 of Repair Round 2's diff confirmed 5 of the 6 Re-audit 1 findings closed, and found one residual gap in the sixth:

1. **DI-S1-04 residual (unrelated-`lib` fallback)**: Repair Round 2 closed the alias-first ordering (an existing editorial-memory copy found under another name gets canonicalized under `lib`), but left one path open: if `lib` was already bound to something genuinely unrelated *and* no already-loaded editorial-memory copy existed anywhere to canonicalize instead, `_load_editorial_memory_lib` silently fell back to loading a fresh copy under the fixed private alias `_documentation_intelligence_editorial_memory_lib` — reintroducing the exact divergent-identity risk this module exists to prevent, via a different path than the one already closed. **Fixed**: that fallback is removed entirely (the private-alias constant no longer exists). When `lib` is occupied by an unrelated module and no existing copy can be canonicalized instead, `EditorialMemoryImportConflictError` is raised before anything is loaded. All previously-passing paths (Documentation Intelligence first, Editorial Memory first, repeated imports, alias-first load, shared identity) remain unchanged and still pass.

## Failure and empty states

`UnknownEvidenceError` (reused, unmodified) — any cited Evidence id that does not resolve. `KnowledgeTypeMismatchError` (reused, unmodified) — a `product_key`/`documentation_key` resolving to the wrong `knowledge_type`, checked unconditionally. `EditorialMemoryImportConflictError` (new, this module only, a subclass of the stdlib `ImportError`) — the name `lib` is already bound to something genuinely unrelated to `editorial-memory/lib` when this module attempts to canonicalize under it; this is an environment-configuration failure, not a Slice 1 logic error, and is expected to be effectively unreachable in this repository's own test/CI environment.
