# Change Specification — Editorial Memory Slices 4–7 (Completion Batch)

This file is the canonical classification record required by `docs/TESTING.md` → "Canonical recording surface." Slices 1–3 (`openspec/changes/editorial-memory/`, `editorial-memory-slice2/`) are closed, merged, and unmodified by this change. This batch adds four sequential, independently-testable capabilities on top of the existing, unmodified Slice 1 storage/lifecycle layer — no redesign of the three-entity model, lifecycle, approval model, or provenance model.

## Process deviation (GOV-01)

This file, `verification-report.md`, and `audit-report.md` did not exist when Slices 4–7 were implemented, locally tested, or first independently audited — that absence was itself GOV-01's finding. This document was written retroactively, after implementation and a first audit round had already happened, not at the normal pre-implementation or alongside-implementation time. It is recorded here explicitly, matching this repository's own established convention for the same situation (see `docs/CURRENT.md`'s Safe PPT Engine Audit Repair 1 entry: "Builds 1–2 must not be described as having passed independent safety audit — they had not been audited when marked complete," and `docs/DECISIONS.md` PROJ-011 (Audit Repair 3)'s explicit "Process deviation" heading in that component's own `spec.md`). No approval is invented anywhere in this document — Editorial Memory's completion is explicitly **not** declared by this file (see "Classification" below and `docs/CURRENT.md`).

## Approved user journey

Existing documentation (a deck, a script, a repo doc — already parsed by the caller into a short claim) is ingested as proposed, never-auto-approved knowledge (Slice 4). A human reviewer can retrieve exactly what's awaiting their decision, filtered by feature area or knowledge type, with enough identity to act on it (Slice 5). As new evidence arrives over time, it confirms, refines, contradicts, or supersedes existing knowledge through the same approval-gated lifecycle Slice 1 already enforces (Slice 6 — proof, not new mechanism). Content that must not remain stored at all — secrets, PII, maliciously ingested material — can be purged by an explicitly-attributed human action, bounded to one record at a time, outside the normal evolution flow (Slice 7).

## Functional requirements

- **Slice 4**: `EditorialMemory.ingest_existing_documentation(...)` records one `Evidence` (`evidence_type=existing_documentation`) and one `KnowledgeState` (`knowledge_type=documentation`), always landing `proposed` — never auto-approved, unlike Slice 2's maintainer-decision bootstrap. Reuses S2-01-style `feature_area`-mismatch rejection and a generalized exact-repeat dedup helper (`_find_matching_evidence_backed_state`, parameterized by `evidence_type` so Slice 2/4 never dedupe against each other).
- **Slice 5**: `lib/review.py` — `list_pending_review`/`list_conflicts`, deterministic, `feature_area`/`knowledge_type`-filterable views over unchanged `get_pending`/`get_conflicts`/`review_required`, carrying KnowledgeItem identity. No new lifecycle; approve/reject/resolve are exactly `approve_state`/`invalidate_state`.
- **Slice 6**: no new capability — `propose_state`/`approve_state` and the `Relation`/`StateStatus` enums already implement confirm/refine/contradict/supersede. This slice is proof-only (dedicated tests, including the first exercise of `Relation.CONFIRMS` in this suite).
- **Slice 7**: `lib/purge.py` — `get_invalidated_by_key`/`list_invalidated_by_*` (dedicated audit access to `invalidated` states, deliberately deferred by Slice 3/5); `purge_evidence`/`purge_knowledge_state` (bounded, human-authorized, one record at a time, tombstone-by-default or full removal, outside the normal evolution flow).

## EM47 audit repair (this record)

An independent Codex audit of the original Slices 4–7 local implementation found 5 code findings and 2 governance findings, all fixed as a further local repair, recorded in this same change:

- **EM47-01**: omitted-`relation_to_previous` exact-repeat detection (Slice 2 + Slice 4) compared each candidate state against a single default relation computed at call time, which changes once the item is no longer empty — a second, otherwise-identical omitted-relation call could fail to match the first and create a spurious duplicate. Fixed: `_find_matching_evidence_backed_state` now compares each candidate against the default relation *that would have applied when that specific state was created* (`NEW` for the item's first state, `REFINES` otherwise), not a single recomputed default. Explicit relations (S2-02) are unaffected.
- **EM47-02**: `purge_knowledge_state`'s `item_id` was passed unvalidated into `JSONStore`'s id-only lookup, which resolves via `Path.glob()` — a glob/wildcard `item_id` could match unintended files. Fixed: new `store.validate_knowledge_item_id()` (same charset as `validate_evidence_id`) rejects anything that isn't a literal, safe generated-id token before purge ever touches disk.
- **EM47-03**: `propose_state`'s new version was `len(item.states) + 1`, which is no longer a safe "next version" once a Slice 7 full-removal purge can shrink `states` without renumbering what remains. Fixed: `version = max(existing versions, default=0) + 1`.
- **EM47-04**: `purge_knowledge_state`'s tombstone mode redacted `content`/`rationale` but left `status` untouched — a purged `current` state remained retrievable as current truth. Fixed: tombstone mode now forces `status = invalidated` unconditionally, and reuses the existing `invalidated_by`/`invalidated_at`/`invalidation_reason` fields (no schema change) to preserve purge attribution/reason in a contract-safe form. Both purge functions now reject a missing/blank `purged_by` via new typed `MissingPurgeAuthorizationError`.
- **EM47-05**: loading a tombstoned Evidence record (or any structurally-incomplete-but-valid-JSON record) raised a raw `KeyError` from `Evidence.from_dict`, not a typed Editorial Memory error. Fixed: `EditorialMemory.get_evidence()` now wraps `KeyError`/`TypeError`/`ValueError` from `Evidence.from_dict` into new typed `CorruptEvidenceRecordError`, chaining the original exception — so `get_current`'s existing `CorruptProvenanceError` wrapping (EM-01, unchanged) continues to catch it, and no raw stdlib exception escapes the typed-error boundary anywhere in this path.
- **GOV-01** (this file and its siblings): the minimum truthful classification/spec/verification/audit record set for Slices 4–7, previously missing.
- **GOV-02**: `docs/CURRENT.md`'s claim that the KnowledgeState-tombstone attribution limitation was "accepted" is corrected — no approving authority reviewed that determination; EM47-04 also resolves the underlying limitation itself (attribution is now persisted via the reused `invalidated_*` fields), so the claim is now moot rather than merely re-justified.

## Round 2 audit repair (this record, supersedes part of the EM47 round above)

A second independent Codex audit found 5 further findings, each a deeper gap Round 1's fixes did not fully close:

- **Finding 1**: EM47-01's fix compared each dedup candidate's expected default relation using its *array index* (`enumerate(item.states)`), which shifts once an earlier state is fully removed by purge - breaking dedup for a surviving later state after an earlier one is purged. Fixed: compared using `state.version == 1` instead - a stable identity that survives purges of *other* states, since `version` is never renumbered for a surviving entry.
- **Finding 2**: EM47-03's fix (`max(existing versions) + 1`) only considered currently-present states, not `superseded_by` references a surviving state can still hold pointing at a version that was later fully removed by purge - risking that number being silently reassigned to an unrelated new state. Fixed: new `_next_version()` helper folds every surviving `superseded_by` value into the same `max()`.
- **Finding 3**: `_find_matching_evidence_backed_state`'s own Evidence lookup called `Evidence.from_dict` directly (bypassing EM47-05's `get_evidence()` fix entirely), so a tombstoned/corrupt candidate's Evidence during a dedup scan still raised a raw `KeyError`. Fixed: the dedup loop now calls `self.get_evidence()`, catching `EditorialMemoryError` and skipping (not crashing on) that candidate.
- **Finding 4**: neither bootstrap path checked the existing item's `knowledge_type` before reusing it - a `record_maintainer_decision` call and an `ingest_existing_documentation` call sharing one natural key could silently blend `editorial`/`documentation`/`product` knowledge under one `KnowledgeItem`. Fixed: both paths now raise new typed `KnowledgeTypeMismatchError` on a `knowledge_type` mismatch, mirroring the existing `feature_area`-mismatch check exactly, before any dedup or mutation.
- **Finding 5**: EM47-04's tombstone approach (redact `content`/`rationale` in place, force `status=invalidated`, reuse `invalidated_*` fields) did not match the approved non-claim tombstone contract and left a state-shaped-but-not-really-a-state entry inside `states`. Fixed, superseding EM47-04's approach entirely: `purge_knowledge_state` now always fully removes the target from `states`, and (tombstone mode, default) writes the canonical `{id, purged_at, purged_by, reason}` `Tombstone` - the same shape `purge_evidence` already produces - to a new dedicated location. **Round 3 finding 2 below found this dedicated-directory approach itself unapproved; superseded again.**
- **GOV-01** (this repair): added the "Process deviation" note above, corrected the Rollback-plan and Founder-preview gates in `verification-report.md` from misleading/incomplete wording to honest statements.
- **GOV-02**: `docs/CURRENT.md`'s active-Editorial-Memory-change pointer, which still named Slice 1 rather than the Slices 4–7 completion batch, is corrected.

## Round 3 audit repair (this record, supersedes Round 2's tombstone storage approach)

A third independent Codex audit found 3 further code findings and 2 governance findings:

- **Round-3 finding 1 (version allocation ignored retained tombstone versions)**: `_next_version()` (Round 2) accounted for `superseded_by` references but not for a version whose tombstone still exists after the tombstoned state itself was removed from `states` - a version could still be silently reassigned to a new state while its tombstone claimed the same identity. Fixed: `_next_version()` now also folds in `JSONStore.tombstoned_versions(item_id)`, read from the raw persisted record.
- **Round-3 finding 2 (unapproved storage-architecture expansion)**: Round 2's `tombstones/` top-level directory was itself an unapproved expansion of the storage layout - the approved contract defines no location for a KnowledgeState tombstone other than the same per-item file a real state already lives in (there is no one-file-per-state location the way Evidence has one-file-per-record). Fixed: the `tombstones/` directory is removed entirely. A tombstone now overwrites its target's *existing array slot*, in place, inside the same `knowledge/<feature_area>/<item_id>.json` file. `JSONStore.load_knowledge_item` filters tombstone-shaped entries (discriminated by the presence of a `purged_at` key, never present on a real `KnowledgeState`) back out of `states` before any ordinary caller sees them, so every existing read path (`get_current`, `get_history`, the Slice 5 review queue, `get_invalidated_by_key`) stays completely unmodified and unaware tombstones exist. Fixing this exposed a second, previously-latent bug: `EditorialMemory._save_item` (the one choke point every mutation path uses to persist a KnowledgeItem) wrote `item.to_dict()` verbatim, which - since `item.states` is always the *filtered* view - would have silently dropped any tombstone on disk the next time anything else about that item was saved. `_save_item` now re-reads the raw record and merges retained tombstones back into what it writes.
- **Round-3 finding 3 (purge write was not atomic)**: Round 2's `purge_knowledge_state` performed the state removal and the tombstone write as two separate `save_*` calls - a failure of the second write after the first succeeded would have left a state permanently gone with no tombstone at all. Moot as a side effect of finding 2's redesign: since the target's array slot is now replaced/removed and the *entire* item record is written in one `save_knowledge_item` call, both purge modes are single-write, and therefore atomic by construction via `JSONStore`'s existing temp-file-then-rename discipline - a write failure leaves the original file, and therefore the original state, completely untouched.
- **Round-3 GOV-01**: `spec.md`/`verification-report.md`/`audit-report.md` said "five pre-existing tests updated" while each enumerating seven test names - corrected to "seven" in both files. The Round 2 "Process deviation"/Founder-preview-Pending/Rollback-plan corrections are confirmed still accurate and are not altered by this fix.
- **Round-3 GOV-02**: `docs/CURRENT.md` wording corrected so it accurately states Slices 4–7 *have* been independently audited (three times now), with re-audit and integration remaining pending - not phrased in a way that could read as "not yet audited."

## Round 4 audit repair (this record)

A fourth independent Codex audit found 2 further code findings and 2 governance findings:

- **Round-4 finding 1 (tombstone recognition was not strictly validated)**: `is_tombstone_entry`'s predecessor logic (Round 3) treated *any* dict containing a `purged_at` key as a tombstone, with no check of its remaining shape or identity. A real `KnowledgeState` that somehow acquired a stray `purged_at` field (corruption, a bug, tampering) would have been silently filtered out of `states` as if it were a legitimate tombstone - silently hiding current/history truth, exactly the failure mode this whole system exists to prevent. Fixed: new `store.is_tombstone_entry(entry, item_id)` requires the entry's keys to match the canonical contract *exactly* (`{id, purged_at, purged_by, reason}`, nothing more or less) and its `id` to parse as `"<item_id>#<version>"` for the containing item specifically. Any `purged_at`-bearing dict that doesn't match raises typed `StorageCorruptionError` - never silently treated as a tombstone, never silently treated as a real state, never a raw `KeyError`/`IndexError`. Used consistently everywhere an entry is classified: `load_knowledge_item`'s filter, `tombstoned_versions`, `_save_item`'s merge, and `purge_knowledge_state`'s target lookup.
- **Round-4 finding 2 (tombstone position/order not preserved across later saves)**: Round 3's `_save_item` fix merged retained tombstones back by *prepending* them before the real states being written - satisfying "not lost" but not "same slot," and not preserving the relative order of real states around them either. Fixed: `_save_item` now walks the existing raw array position by position - a tombstone entry is carried through unchanged at its own index; a real-state entry at a version already known is replaced in place with its updated dict; only a genuinely new version (never before in the raw record) is appended at the end. A tombstone now stays in its exact original array slot through any number of subsequent, unrelated mutations, and reload.
- **Round-4 GOV-01**: two stale/inconsistent pieces of Round 3's own governance wording - "both rounds" left over from before Round 3 itself was added, and a stale reference to the just-removed `load_knowledge_state_tombstone` accessor in a profile-specific gate row - corrected. A separate arithmetic error was also found and fixed: Round 3's own report conflated two *different* test sets (Round 2's 7-test tombstone-contract set and Round 3's own, smaller 6-test accessor-removal set) as if they were "the same seven-test set."
- **Round-4 GOV-02**: `docs/CURRENT.md` updated to state plainly that Slices 4–7 have now been independently audited four times, with comprehensive re-audit (covering all four rounds) and integration remaining the pending next steps.
