# Change Specification — Browser Verification Pilot, Engineering Slice 1

This file is the canonical classification record required by `docs/TESTING.md` → "Canonical recording surface," per the same convention used by `openspec/changes/editorial-memory-slices-4-7/`. It records only the narrow engineering bridge from a bounded browser observation to Editorial Memory Evidence — not a browser automation framework, not a redesign of Editorial Memory, not the pilot's overall completion.

## Context

Per the founder-locked decision [[Browser Verification Pilot Requirement]] (Obsidian `Projects/Bridge4PS Documentation Engineer/Decisions/Browser Verification Pilot Requirement.md`, `BDE-DEC-0004`), Browser Verification may not become a routine Editorial Memory evidence source until a dedicated pilot passes on two independent dimensions: **AI understanding** (UI/workflow/terminology/role-permission interpretation, uncertainty handling, avoiding invented behavior) and **engineering** (Evidence generation, provenance preservation, verification scope, Editorial Memory integration, lifecycle correctness, no silent overwrite).

Three AI-understanding pilot runs (Test 1: bounded passive observation; Test 2: multi-step state-transition observation with reversibility proof; Test 3: role/permission epistemic-safety test, explicitly concluding no general permission rule was established) exercised the live Bridge4PS web app and produced structured, DIRECTLY-OBSERVED/INFERRED/UNKNOWN-separated reports. This change is **Engineering Slice 1**: the smallest safe integration proving those observations can become durable, typed, round-trippable Editorial Memory Evidence — Evidence only, never automatically promoted to Knowledge.

## Approved user journey

A bounded browser-observation pilot run produces a structured record: one workflow description, one or more directly-observed facts (required, non-empty), optional inferences, optional unknowns, and an optional uncertainty note — kept as four structurally separate categories throughout, matching the epistemic-safety discipline the AI-understanding tests established. That record becomes one ordinary `Evidence` row (`evidence_type=browser_observation`) via the existing, unmodified `EditorialMemory.record_evidence`. Nothing about recording it creates, proposes, or approves any `KnowledgeItem`/`KnowledgeState` — the existing maintainer review/lifecycle (`propose_state`/`approve_state`) remains the only, unmodified path from this Evidence to Knowledge, exactly like every other Evidence type already in this system.

## Functional requirements

- New `editorial-memory/lib/browser_evidence.py`: `BrowserObservation` (frozen dataclass: `workflow`, `direct_observations` [tuple, required non-empty], `inferences`, `unknowns` [tuples, default empty], `uncertainty` [optional str]) with a deterministic, sorted-key JSON `to_notes()`/`from_notes()` pair carried inside the existing `Evidence.notes: Optional[str]` field — no schema change to `models.Evidence`.
- `record_browser_observation(memory, ...)`: validates all inputs, forces `evidence_type=EvidenceType.BROWSER_OBSERVATION` (never caller-supplied), and delegates the actual write to the existing, unmodified `EditorialMemory.record_evidence`.
- `get_browser_observation(evidence)`: the typed-safe inverse, recovering the structured payload from a persisted `Evidence` record.
- Two new typed errors (`errors.py`): `InvalidBrowserObservationError` (write-time) and `MalformedBrowserObservationError` (read-time) — following this module's own established typed-error-per-boundary convention exactly.
- `models.py`, `store.py`, `memory.py`'s `record_evidence`, `purge.py`, `review.py`, `retrieval.py`: **zero changes**.

## Repair Round 1 — Audit 1 (FAIL) findings

An independent audit of the initial Engineering Slice 1 implementation returned **FAIL**, finding strictness gaps in both validation boundaries, plus a governance-completeness gap. All four fixed as local Repair 1, recorded in this same change:

- **Finding 1 (loose persisted-notes parsing)**: `BrowserObservation.from_notes()` used a *subset* check for required keys (silently accepted extra keys), compared `schema` with `!=` (Python's `True == 1`, so a boolean `schema` value would have silently passed as valid), and called `tuple(...)` directly on `direct_observations`/`inferences`/`unknowns` without first confirming they were JSON arrays — a persisted string value there would have been silently exploded into one entry per character instead of rejected. Fixed: exact key-set equality; `type(schema) is int and schema == 1` (excludes `bool`, a `int` subclass in Python, by type rather than value); a new `_require_json_str_list` helper rejects anything that isn't a genuine `list`, rejects empty `direct_observations`, and rejects any non-string/blank entry — all before any `tuple()` conversion is attempted. `workflow`/`uncertainty` are now explicitly type-checked as well.
- **Finding 2 (loose write-boundary validation)**: `record_browser_observation`'s helper called `tuple(value)` on whatever was passed for `direct_observations`/`inferences`/`unknowns` — a bare string would have been silently character-split (the identical bug as finding 1, on the write side), a non-iterable value (e.g. an `int`) would have raised a raw, untyped `TypeError`, and a `set`/`frozenset` would have produced nondeterministic serialization order. `verification_scope` was passed straight through to the existing `record_evidence` with the same unvalidated shape, and `evidence_quality` was never type-checked at all. Fixed: new `_require_ordered_str_sequence` explicitly rejects `str`/`bytes`, explicitly rejects `set`/`frozenset`, requires `list`/`tuple`, and validates every entry — applied to `direct_observations`/`inferences`/`unknowns` *and* `verification_scope` (validated in `browser_evidence.py` itself, before `record_evidence` ever sees it, since `record_evidence` is existing/unmodified code); `evidence_quality` is now checked against `isinstance(..., EvidenceQuality)`.
- **Finding 3 (regression coverage)**: 41 new focused tests added (`test_browser_evidence.py`, 22 → 63), covering every malformed shape named in findings 1–2 on both boundaries, plus an explicit `captured_at` round-trip test (present and omitted cases) and a deterministic-ordering proof (list vs. tuple input serialize identically; non-alphabetical input order is preserved exactly, never sorted).
- **Finding 4 (governance completeness)**: this `spec.md`, `verification-report.md`, and `audit-report.md` — the minimum classification/verification/audit record set this repository's convention (`docs/PIPELINE.md` → "Canonical skills-output mapping") requires for any change — did not exist for Engineering Slice 1 until this repair. Added here. `docs/CURRENT.md`'s stale "no `browser_observation` producer... exist yet" line (from before this slice existed) and `docs/DECISIONS.md` (new `PROJ-028`) are corrected/added — narrowly, for this change only; the large, separately-flagged pre-existing drift in `docs/CURRENT.md` regarding Editorial Memory Slices 4–7's actual merged/integrated state (found during a prior read-only repository-recovery pass) is explicitly **not** touched by this change, being out of this repair's scope.

## Repair Round 2 — Closure Audit 2 (FAIL) findings

A closure audit of Repair Round 1's diff also returned **FAIL**, finding Repair 1's own fix for finding 1 (strict persisted-notes parsing) was still not strict enough against two further malformed-JSON shapes, plus a governance-chronology misstatement in `audit-report.md`'s own prior verdict. All three fixed as local Repair 2, recorded in this same change:

- **Finding 1 (duplicate JSON keys)**: `BrowserObservation.from_notes()` called plain `json.loads(notes)`, which silently accepts a JSON object containing a duplicate member name and keeps only the last-seen value — e.g. a persisted `notes` string with two `"workflow"` keys would silently resolve to the second value, never rejected. Fixed: `json.loads` is now called with a custom `object_pairs_hook` (`_strict_object_pairs_hook`) that raises typed `MalformedBrowserObservationError` the instant a duplicate key is found, at any nesting level.
- **Finding 2 (oversized JSON integer raw `ValueError`)**: an extreme-digit-count integer literal anywhere in the persisted JSON (e.g. a 5000-digit `schema` value) would reach Python's own int-string-conversion guard *inside* `json.loads` itself, raising a raw `ValueError` before this module's `try`/`except` around `json.loads` could distinguish it from a genuine parse failure — and that guard's threshold varies by Python version and is process-configurable. Fixed: `json.loads` is now also called with a custom `parse_int` hook (`_strict_parse_int`) enforcing a fixed, version-independent digit-count bound (`_MAX_JSON_INT_DIGITS = 18`) before ever calling `int()` on the literal's text, raising typed `MalformedBrowserObservationError` deterministically on every supported Python version.
- **Finding 3 (governance chronology)**: `audit-report.md`'s own prior verdict misstated Audit 1 as "PASS WITH FINDINGS" rather than **FAIL** — a materially different verdict. Fixed: `audit-report.md` rewritten to state the accurate chronology (Audit 1 FAIL → Repair 1 → Closure Audit 2 FAIL → Repair 2 → next closure audit pending); `docs/DECISIONS.md` (`PROJ-028`) and `docs/CURRENT.md` corrected to match; this `spec.md` and `verification-report.md` reviewed and updated only where their own content (test counts, round numbering) had gone stale as a direct consequence of Repair 2 — neither file had itself misstated a PASS/FAIL verdict, since neither carries a verdict of its own (that lives in `audit-report.md` only).

11 new focused tests added (`test_browser_evidence.py`, 63 → 74): duplicate `workflow` key specifically; duplicate keys at three other field positions; a 5000-digit `schema` integer through both `from_notes()` and `get_browser_observation()`; combined no-raw-exception proofs for both bug classes; a sanity check that ordinary, valid payloads still parse correctly under the new strict decode hooks.

## Repair Round 3 (evidence-coverage only, no production change)

A low-severity closure finding noted that Round 2's duplicate-JSON-key coverage exercised only `from_notes()` directly and only top-level duplication - not `get_browser_observation()` (the path every real caller actually uses to read a persisted observation back) and not a duplicate key nested inside another JSON object in the document. Confirmed by direct reproduction that the existing `_strict_object_pairs_hook` (Round 2) already handles both cases correctly - it applies to every JSON object `json.loads` encounters, at any nesting level, regardless of which function calls `json.loads`. **No production code was changed in this round** - this closes a test-coverage gap only. 2 new tests added (`test_browser_evidence.py`, 74 → 76): a duplicate `workflow` key reaching `get_browser_observation()` via a real persisted `Evidence` record; a duplicate object key nested inside a `direct_observations` list entry.

## Failure and empty states

`InvalidBrowserObservationError` (write-time: blank/wrong-typed text field; `direct_observations`/`inferences`/`unknowns`/`verification_scope` given as a string, set, non-iterable, or containing a non-string/blank entry; empty `direct_observations`; invalid `evidence_quality`). `MalformedBrowserObservationError` (read-time: malformed JSON; non-object top level; a duplicate JSON object key at any nesting level; a JSON integer literal longer than 18 digits anywhere in the document; extra/missing keys; `schema` not exactly integer `1`; non-string `workflow`/`uncertainty`; any of the three list fields not a JSON array, empty (`direct_observations` only), or containing a non-string/blank entry; wrong `evidence_type` on the source `Evidence`; missing `notes`). No raw `TypeError`/`ValueError`/`AttributeError`/`KeyError`/`json.JSONDecodeError` reaches any caller through either boundary — proven by dedicated tests.

## Security and privacy requirements

Unchanged from Slice 1–7: no credentials, no network access inside this module (network access, if any, happens entirely in the caller that produced the `BrowserObservation` fields — outside this change's scope), local structured-text persistence only, via the existing unmodified `JSONStore`. This change adds no new storage location and no new mutation capability beyond writing one more `Evidence` record through the existing path.
